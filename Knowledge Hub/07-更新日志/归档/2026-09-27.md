# 2026-09-27

## Azure Vanguard — 系统正规化路线 + 配置表系统落地

用户拍板系统建设顺序：**配置表 → 物品/背包/货币 → 账号 → 网络传输层+服务端骨架 → 玩家数据上服务器 → 商店（服务端权威）**；热更管线在第二步后并行。服务器愿景：热更包上传服务器、商店物品由服务端下发、玩家数据服务端存储、购买等操作发服务端裁决后客户端更新。

数据两分法（用户定调）：
1. 网络传输/实时变动（商店表等）→ Excel+二进制转换，运行时二进制解读
2. 确定性固定配置（角色/敌人：图标、BEclip、id）→ SO
- 我补充的边界：玩家运行时数据（背包/配队）属于第 1 类但**不经 Excel**，直接 MessagePack；Excel 只是"策划可编辑表"的编辑器。
- 二进制 vs JSON：用户直觉正确——msgpack 体积约 JSON 的 30%~60%；Excel 成为源头后"JSON 可读"理由消失，.bytes 是构建产物，`ConvertToJson` 随时可读。

### 配置表系统（当日落地，全链路验证通过）

- **运行时骨架**（Core.Gear/ConfigTable/ 六文件）：ConfigTableFile 信封 / IConfigTableRow / DataTable（主键索引，重复主键报错保留先者）/ ITableSource / AddressableTableSource / DataTableManager（缓存 + SetSource 可替换，为热更/服务端推表留口）。
- **导出工具**（Tools/ExcelTableExporter，dotnet 9 控制台 + ClosedXML）：--init 生成模板（表头/类型行/示例数据）、无参全量导出、校验报错带单元格坐标、JSON 调试副本带字段名且中文不转义（UnsafeRelaxedJsonEscaping）。
- **MessagePack 互操作三坑**（详见 [[modules/azure-vanguard]] 配置表系统节）：
  1. `Dictionary<string,object>` 信封的 rows 掉进 DynamicObjectTypeFallbackResolver 反射序列化 → 工具端改强类型 `TableEnvelope`（[MessagePackObject] + [Key("列名")]）；
  2. 动态格式化器只认 public 类型；
  3. `ItemRow.PrimaryKey` 漏标 → "all public members must mark KeyAttribute or IgnoreMemberAttribute"，补 `[IgnoreMember]`。
- **端到端验证**：Excel 3 行示例 → 378 B bytes（json 622 B，二进制 61%）→ 引擎内反序列化逐字段正确 → TryGet(1002)=True / TryGet(9999)=False → Addressables 入组 ConfigTables（地址 ConfigTables/ItemTable，标签 DataTable）。
- ClosedXML 坑：`cell.Value` 是 XLCellValue 结构，不接受装箱 object，需按具体类型分支写入。
- dotnet 环境 9.0.200；工具直接引用 Plugins 里的 MessagePack.dll（netstandard2.0 在 .NET 9 可加载），两端零版本漂移。

## Azure Vanguard — 服务端口径对齐 + 物品模型定稿

用户确认三点：① 货币/商店等走服务端权威（请求→服务端校验→改→持久化→回发→客户端只更新缓存，v1 不做乐观更新）；② 线上只跑 MessagePack 二进制，JSON 仅供调试，机密性靠 TLS；③ 客户端无数据库概念；服务端先文件存储。

- 我提出的"扣款与发货必须原子所以迟早要数据库"被用户纠正：操作全在服务端一个同步函数内完成，正常路径不存在扣钱没给货。修正后真正要做的只有两件事：**玩家全量状态单文档持久化 + 临时文件 `File.Replace` 原子替换写**（防撕裂），正确性即闭环；数据库买的是查询/备份/扩容，是规模问题不是正确性问题。存储层留 `IPlayerDataStore` 抽象。
- 真正剩余的风险：**响应丢失 ≠ 操作失败**（服务端成功但回包丢了，客户端重试 → 重复扣钱）→ 请求带 requestId，服务端记处理过的请求重发原结果。文件存储和数据库都不自动解决，必须自己写。
- 物品模型定稿：货币是物品（type 之一）；type(int) 管分类、tags(string) 管功能；tags 逗号分隔多标签，注册表工厂分发（同 BetterHSMAbilitySchemeCatalog 惯例）；体力不走背包；玩家持有量服务端权威。

## Azure Vanguard — 服务端技术栈 + 战斗同步方案定稿

用户问服务端选型（C++ 还是 C#、MessagePack 有无 C++ 库、多线程承担客户端开销）：

- **定稿 C#/.NET，否决 C++**。论据：服务端 I/O 密集非 CPU 密集（5 万条/秒 ≈ 半核计算量）；msgpack-c 存在但契约两套人肉同步，丢掉共享协议核心优势；单人 C# 团队跨语言维护成本。多线程姿势 = async/await 连接层 + 每玩家 Channel 串行（actor），不是手写线程池。
- 存储定稿：玩家全量状态单文档持久化 + File.Replace 原子替换；IPlayerDataStore 抽象留换库余地；requestId 幂等必须自写。
- **战斗方案**（用户提出 RTS+塔防混合、八人编队、局内点数经济，并主动提议"关键数据留存上传校验"路线，我确认方向并落点）：帧同步不做（PVE 偏单机零收益）；服务器全量重模拟不做；**客户端本地权威模拟 + 结算战报 + 台账/规则校验**。关键杠杆 = 点数收入规则化（波次奖励+时间供给），支出全指令化 `{seq,type,cost,params}`，服务器推算上限对账。用户确认同意。
- 三个刻意后置项：账号身份选型（第 3 步立项定）、服务器部署托管（骨架出来再定）、真人 PvP 帧同步（届时再议）。
- 方案全文见 [[modules/azure-vanguard]] 服务端与战斗同步方案节。

## Azure Vanguard — YAGNI 拍板 + 配置表格式再确认 + 服务端部署定稿

- **背包不建查询层**（用户拍板"什么时候用到什么时候写"）：GearBar 只需货币 ID 常量 + `GetCount` 直填；物品名/图标查询层等背包格子/详情页 UI 出现再建。
- **用户提议 ItemTable 转 JSON**，被两个论据拦下：①"作弊改了没用"对 JSON/二进制无区分度（防篡改靠结算以服务器为准 + 战报带配置表版本，不靠格式）；②"网络更轻量"方向反了——实测同表 binary 469B vs json 776B。维持 Excel→MessagePack + JSON 仅调试副本。
- **服务端部署分阶段定稿**：本机 console（双端同机断点调试）→ 联测穿透/轻量云 → 上线租 Linux 云（publish + systemd）；唯一代码要求 = 服务器地址可配置；ICP 备案/版号为公开运营前置项，现阶段不涉及。
