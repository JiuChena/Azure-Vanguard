## Azure Vanguard — 需求拆解 + 角色数值体系定稿

### 系统全景拆解（回答"还有别的吗"）

玩法层：战斗、角色养成（角色仓库/等级/星级/技能/突破）、抽卡（**随机必须服务端裁决**）、商店（服务端权威）、背包（台账已有）、任务、体力、活动（后期）。
数据层：**玩家数据中心**（统一玩家档案=将来上服务器的"单文档"，角色仓库/任务进度/保底记录/体力时间戳都挂它——晚做会返工，建议提前）、时间系统（体力恢复/商店刷新/每日重置依赖）、配置表系统（已落地）。
平台层：账号（第 3 步）、网络传输层（requestId 幂等自写）、服务端骨架、热更管线（平行推进）、支付/上报/本地化（远期）。
建议顺序：①战斗框架 → ②玩家数据中心 → ③角色仓库+养成 → ④体力+时间 → ⑤任务 → 账号/网络/服务端 → 抽卡/商店接服务端裁决。

### 数值表方案（用户拍板，本轮动工）

- **SO/表边界收窄**：SO = 表现绑定（图标/BEclip/Prefab 等资产引用）；数值 = 实时变动（调平衡）→ Excel 表。判定标准一句话：**服务端要不要读**——服务端读不了 SO，数值全走表（战报校验要服务端复算）。
- **乘区公式**：`最终属性 = (base × levelMult(level) + Σ已解锁bonus节点) × starMult(将来)`。服务端复算 = 同一段公式代码跑同一批表；养成新维度 = 加乘区/加区，战斗侧零改动。接缝：`CharacterStats.Calculate(id, level, star, ...)` 单一查询入口，战斗 v1 恒传 star=1。
- **6 张表**：CharacterTable（12 属性+5 技能引用列）/ LevelTable（level/multiplier 共享曲线）/ SkillTable（骨架）/ SkillEffectTable（效果行）/ UnlockNodeTable（天赋+属性加成节点，无等级解锁制）/ BreakthroughTable（突破阶段）。
- **技能两层**（解决"一个技能多效果"）：技能是骨架，效果一行一个。示例"回自身20%+回全队10%+5×5减速50%" = 3 行效果。等级成长跟效果走：`某级数值 = value + growth × (level−1)`，**不逐级建行**（10级×N效果会爆炸）。运行时 effectType → 执行器注册表分发（同 ItemFeatureCatalog 惯例）。
- **id 编码**：skillId = 角色id×100+槽位（01普攻/02E/03Q，如 22102）；effectId = skillId×100+序号（如 2210201）。看 id 知归属，零映射表。
- **突破**：行=阶段（levelCap 20→40→50→60→70→80），costItems 格式 `itemId:count` 逗号分隔（金币也是物品，id=1）；unlockNodeIds = 突破附带解锁的属性加成节点（原神式），与 UnlockNodeTable 自带 cost 的独立材料解锁并存。
- **升级经验**：用户拍板**不放表**——公式是死的，写业务逻辑。
- **表地址新规**：角色模块表放 `Assets/Module/Unit/Character/`（`Excel/` 源 + `ConfigTables/` 产物）；Addressables 逻辑地址规范不变（`ConfigTables/<表名>`），ItemTable 等仍走 ConfigSources/Excel → Assets/ConfigTables。导出工具支持目录对，无参全量覆盖全部目录对。
- **UnitConfig 聚合根**（用户设计）：UnitConfig 实时引用该角色的数据表 .bytes，**角色入队加载 UnitConfig 一个入口全部到位，卸载也跟随**。基类 UnitConfig（int id + behaviorClips）→ CharacterUnitConfig（dataTables[] + breakthroughTable，突破仅角色有）；敌人 SO 将来另开子类继承基类。资源生命周期跟 UnitConfig 走，数据生命周期归 DataTableManager 缓存共享（8 人编队不重复反序列化，EnsureTable 注入入口待实现）。
- 角色养成条目形状（玩家数据侧声明）：`level + exp + breakStage + skillLevels(普攻/E/Q) + unlockedNodes[]`。

### 设计决策

- **版本号语义澄清**：档案 `version` = schema version（数据结构迁移抓手，载入时 switch-case 迁移链逐版升级），**不是**热更包版本（那是资源管线的事）。
- **分域档案 + 门面，不搞单文件大档**：现有两域（资料/背包）已按"每域一 Manager + 带 version 的 MessagePack 文件"跑通，推翻纯迁移成本零收益；本地分文件容错好；服务器单文档 = 上传时组装，不要求本地单文件。返工风险真正在**条目形状/版本策略/入口统一**，本轮钉死：Data 根对象（version 首字段 + [Key] 只追加不重排）+ Manager 单例（唯一存档者、变更即保存、Normalize 防脏）+ PlayerDataCenter 门面跨域操作。
