# 服务端与网络【骨架】

> 状态：**方案定稿（2026-09-27），未开工**。路线图位次 ⑥（[[01-项目总览/系统路线图]]）。本文保存定稿方案，动工时展开为实文档。

## 服务端技术栈（定稿）

- **.NET C# 控制台，否决 C++**：本服务端 I/O 密集（登录/背包/购买校验）非 CPU 密集，5 万条/秒消息 ≈ 半核计算量，async/await 主场；msgpack-c 需两套契约人肉同步，丢掉共享协议优势。C++ 只在将来出现帧驱动 CPU 密集子系统（服务端实时战斗）时按模块拆分考虑
- **与 Unity 共享协议程序集**：消息类纯 C#、不引 UnityEngine（日志走接口/条件编译），客户端服务端同一份 [Key] 契约
- **并发模型**：连接层 async/await 全异步；逻辑层**每玩家 Channel 消息队列串行处理**（actor 模式，单玩家状态无锁）。单进程起步，规模到了再拆 gate/逻辑进程分片
- **存储**：玩家全量状态**单文档持久化**（每玩家一份 MessagePack .bin）+ 临时文件 `File.Replace` 原子替换写（防撕裂，不存中间态）；**不做跨文档拆分**（两份文件两笔写之间崩溃才有一致性窗口）。存储层留 `IPlayerDataStore` 抽象，将来换 SQLite/MySQL 只动这一层——数据库是规模/运维问题，不是正确性问题（用户纠正确认）
- **消息纪律**：请求带 `requestId`，服务端记录已处理请求，重复请求重发原结果（防"响应丢失≠操作失败"的重试重复扣费）；此机制文件存储与数据库都不自动提供，必须自写
- **部署分阶段（定稿）**：开发期本机 console（与 Unity 同机双端断点调试，C# 全栈红利）；联测期内网穿透（frp/Tailscale）或最低配轻量云；正式运营租 Linux 云服务器（`dotnet publish` 自包含 + systemd 守护）。**对代码唯一要求：服务器地址客户端可配置，不 hardcode**。前置事实：国内云主机公网服务需 ICP 备案，正式商业运营游戏涉版号

## 战斗同步（RTS+塔防混合，八人编队 PVE，偏单机）

- **客户端本地权威模拟 + 战报同步**。手感无损，符合偏单机定位
- **帧同步不做**：无队友要同步（零收益），确定性化（浮点/物理/随机/引擎管制）+ 战斗引擎服务器可跑 = 双份成本，PvP 实时对抗立项时再议
- **服务器全量重模拟不做**（同上成本）
- **防作弊 = 台账 + 规则校验**，核心杠杆：**局内点数收入做成规则可算**（波次奖励+时间供给，服务器不模拟战斗即可推算任意时刻点数上限）
- 局内所有功能（放置/复活/买道具/升属性/buff/场内道具）全是指令交易 `{seq, type, cost, params}`；单局指令流水本地留存，**结算时整包上传战报**（流水+结果+配置表版本），断线重连续传
- 服务器校验分层：本体数值（等级/星级/装备）服务器结算下发客户端只缓存 → 经济台账（Σ支出 ≤ 推算上限、价格对表）→ 布阵规则（≤8 人、每人一次、点位合法）→ 结算合理性（通关时间 ≥ 理论最短）。快照抽检/服务器简模重放后置，排行榜等高价值场景才上
- 作弊收益被压缩为"单局内体验"，持久收益（奖励/货币/成长）全部经校验落地
